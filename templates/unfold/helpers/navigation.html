{% comment %} Two-column admin navigation: a narrow icon rail, and a panel showing the items of whichever rail section is selected. Overrides unfold/helpers/navigation.html — the project templates directory is ahead of app dirs in TEMPLATES["DIRS"], so this file wins over the package's. Unfold ships a single column: every group and every item stacked in one list. With five groups and eleven items that is a wall you read past rather than a thing you navigate. The rail turns the top level into five targets you aim at, and the panel only ever shows one group's items. WHICH SECTION IS OPEN. Rendered server-side from the current URL, matching EITHER a group's own index page or one of its model pages, then falling back to the first group. Both halves are needed. Item matching alone leaves every app index — the exact page a rail icon opens — matching nothing, so the panel fell back to the first group and appeared frozen: you clicked Core and kept looking at Chat. Matching the group link alone would miss every changelist. Neither is ambiguous now that one group means one app. `active` and `section` are separate on purpose. The panel always needs SOMETHING open, so it falls back to the first group; the rail highlight must not, or the dashboard — which belongs to no app — lights up Chat and claims you are somewhere you have not been. `active` stays empty there, and the logo takes the highlight instead, since that is the page you are on. Each rail icon opens its app's index page. That only works because the groups ARE the apps: one group per app, listing exactly what that app registers. An earlier version grouped by job instead, and then had nowhere honest to point — two groups shared an index, and clicking "Tenants" landed on a page headed "Core administration". Each rail icon is a LINK to its group's first page rather than a toggle. Clicking a top-level section should take you somewhere; a rail that only reveals a list costs two clicks to go anywhere. The page it lands on is active, so the panel opens on that group on its own and the highlight follows without any client-side state changing hands. STYLING lives in core/static/core/unfold-overrides.css under `.pf-nav`, NOT in Tailwind classes here. Unfold ships a prebuilt stylesheet, and Tailwind only compiles the classes it saw at build time — so an invented utility like `w-[56px]` would simply not exist in the bundle and would silently do nothing. Semantic class names in our own sheet are the only reliable route, and they match how the rest of the admin theme is already overridden. {% endcomment %} {% load i18n unfold %}
